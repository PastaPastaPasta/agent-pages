base-sdk: the fork and its upstream path

Snapshot 2026-11-05 01:17Z. Built from the fork's git history, GitHub, and the program's plan, status and design records. Security-sensitive items are left out.

What base-sdk is. dashpay/base-sdk is kwvg's new Rust library of Dash building blocks: number and hash types (dash-types, dash-num), keys and BLS signatures (dash-pkc), X11 proof of work (dash-pow), transactions (dash-primitives), scripts, chain parameters (dash-params) and P2P messages (dash-p2p-core).

Why there is a fork. The Rust node must read every byte exactly as Dash Core does. base-sdk didn't yet cover v24, the masternode overlay messages, or Core's BLS edge cases. So the agent keeps a local branch, node/base-sdk, lands that work there first, and pins the node to it. Pieces are then rebuilt in kwvg's conventions and proposed upstream, following a 30-unit plan.

    Upstream roadmap: 30 planned units

    The agent's plan (design record BSX §7.3) breaks the fork into 30 small PR units in three tiers. Tier 1 is strict fixes with no Core-compat leniency, tier 2 needs a decision on one leniency, and tier 3 needs a design call from kwvg. Each unit is matched to the real PRs by commit content.

    Deviation catalogue

    Before proposing anything upstream, the agent catalogued every place the fork behaves differently from upstream (design record BSX). There are 88 items. Most are strictness fixes, exact Core limits, v24 data and new message types that upstream should want anyway. Fewer than half are "leniencies", where the fork deliberately accepts input as Core does even though a strict design would refuse it.

    Strictness, data or APILeniency the node needs (a)Leniency to remove or move node-side (c)Other

    Headlines from the catalogue

    • Most of the fork is not leniency; it can go upstream once reshaped to kwvg's patterns (tier 1).
    • The leniencies consensus needs sit in two places: Core's BLS wire rules and Core's lossy NetInfo reader. Both are decoder-level, so upstream gets either named Core-compat functions or nothing. That's kwvg's call.
    • Four upstream bugs made the strict decoder reject honest v24 traffic: the senddsq/qsendrecsigs flag, SPV wallets' 9-field version, 8000-header headers2 replies, and govsync's bloom-filter tail. Three of the four are now fixed upstream or in open PRs.
    • Most remaining (c) leniencies are P2P-handler tolerances. They should leave base-sdk and live in the node instead.

    Glossary

    Core / the reference
    Dash Core (dashd), the C++ node, treated as the definition of correct behaviour.
    Decode domain
    Exactly which byte strings a parser accepts and how it reads them. "As Core does" means the same accept/reject verdicts, the same values, and the same bytes consumed.
    Leniency
    Accepting input a strict parser would refuse, because Core accepts it. (a) means the node needs it; (c) means it should be removed or moved into the node.
    Special transactions
    Dash transaction types beyond payments: masternode registration and updates (ProTx), coinbase payload (CbTx), quorum commitments, asset locks and unlocks.
    v24
    The next Dash Core major release; it changes several special-transaction formats. Mainnet signalling starts around 11-09.
    Overlay messages
    Dash-only P2P messages: ChainLocks, InstantSend, quorum/DKG traffic, masternode lists, CoinJoin and governance.
    BLS legacy vs basic
    Dash used a pre-standard BLS encoding ("legacy", via the relic C library) before v19, then the IETF "basic" scheme. Both still appear on chain.
    Exotic points
    Legacy BLS values that aren't proper group elements but that Core still accepts and computes with.
    Corpus / vectors
    Test cases recorded by running Dash Core, so tests compare against Core's real answers.
    just comb
    base-sdk's per-commit check: every commit in a PR must build, lint and test on its own.
